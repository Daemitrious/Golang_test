# Search Trends Service

Сервис считает Top-n популярных поисковых запросов за последние условные 5 минут.

Схема:

External Search Service -> NATS -> Go consumer -> sliding window storage -> cached top -> HTTP API

## 2. Контракт данных

Брокер: NATS.

Subject: 'search.events'.

Пример payload из брокера:

json

{
  "event_id": "018f3c0b-2f21-7a9f-b9e8-1f5d7c1b9c01",
  "query": "кроссовки",
  "user_id": "user-123",
  "session_id": "session-456",
  "ip_hash": "iphash-789",
  "timestamp": "2026-05-23T12:00:00Z"
}


Поля:

- 'event_id' нужен для дедупликации повторно доставленных событий.
- 'query' нужен для подсчёта популярности поискового запроса.
- 'user_id' нужен для простой защиты от накрутки одинаковых запросов одним пользователем.
- 'session_id' оставлен для будущего расширения anti-abuse логики.
- 'ip_hash' оставлен для будущего анализа источников всплесков без хранения сырого IP.
- 'timestamp' нужен для расчёта окна за последние 5 минут по времени события.

Валидация:

- пустой 'query' отбрасывается;
- пустой 'event_id' отбрасывается;
- пустой 'user_id' отбрасывается;
- слишком длинный payload отбрасывается;
- слишком старое событие отбрасывается;
- timestamp из будущего выше допустимого skew приводится к текущему времени.

## 3. Обоснование архитектуры

Выбран NATS, потому что он простой для локального запуска, быстро интегрируется с Go и подходит для потока небольших событий.
Основное хранилище находится в памяти процесса.

Используется sliding window на 5 минут:

- окно разбито на секундные бакеты;
- каждый бакет хранит счётчики query за конкретную секунду;
- общий 'map[query]count' хранит сумму по всему окну;
- при истечении времени старые бакеты вычитаются из общего счётчика.

При поступлении события сервис:

1. проверяет размер payload;
2. парсит JSON;
3. нормализует query;
4. проверяет обязательные поля;
5. проверяет 'event_id' на дубликат;
6. проверяет stop-list;
7. применяет anti-abuse по 'user_id + query';
8. увеличивает счётчик в секундном бакете;
9. увеличивает общий счётчик запроса;
10. инвалидирует cached top.

Ручка '/top' отдаёт заранее подготовленный 'cachedTop'.

Причина: по условию чтений топа ожидается в 10-50 раз больше, чем входящих событий. Поэтому выгоднее держать готовый top, чем сортировать все query на каждый HTTP-запрос.

Stop-list хранится как 'map[string]struct{}'. Проверка стоп-слова выполняется за O(1). Управление stop-list доступно через HTTP API без перезапуска сервиса.

Админские stop-list ручки закрыты заголовком 'X-Admin-Token', если задан 'ADMIN_TOKEN'.

Метрики отдаются через '/metrics' в формате Prometheus. Grafana подключена к Prometheus для визуализации.

## 4. Trade-offs и бизнес-логика

### Бизнес-логика

Сервис решает задачу виджета "Сейчас ищут".

Главное бизнес-требование: быстро отдавать Top-N популярных поисковых запросов за последние 5 минут.

Сервис не ищет товары и не создаёт поисковые события. Он читает события из брокера, фильтрует их, обновляет статистику и отдаёт готовый top через API.

### Выявленные неточности постановки и решения

| Проблема | Решение |
|---|---|
| Не указан формат сообщения в брокере | Зафиксирован контракт 'SearchEvent' |
| Не указано, как определять уникальность события | Добавлен 'event_id' |
| Не указано, считать по времени получения или времени события | Используется 'timestamp' события |
| Не определено, что считать накруткой | Простая эвристика по 'user_id + query' |
| Не указано, как управлять stop-list | Добавлен HTTP API |
| Не указано, что делать с мусорными сообщениями | Валидация + метрики bad/invalid events |
| Не указано, хранить ли данные после рестарта | Состояние in-memory, после рестарта сервис пустой |
| Не описана защита админских ручек | Добавлен 'X-Admin-Token' для stop-list API |

### In-memory storage вместо базы данных

Причина выбора:

- данные нужны только за последние 5 минут;
- сервис по условию стартует пустым;
- чтений топа больше, чем входящих событий;
- память даёт минимальную задержку;
- проще локальный запуск.

Компромиссы

- после рестарта статистика очищается;
- несколько реплик будут иметь разное состояние;
- для production можно вынести состояние в Redis, Kafka Streams, ClickHouse или отдельный aggregator.

### Sliding window вместо хранения всех событий

Причина выбора:

- бизнесу нужен только актуальный top;
- старые события не должны влиять на виджет;
- не нужно хранить историю ради этой ручки.

Компромисс:

- сервис не отвечает на исторические запросы;
- это принято сознательно, потому что задача только про последние 5 минут.

### Cached top вместо пересчёта на каждый запрос

Причина выбора:

- '/top' должен быть дешёвым;
- чтений ожидается больше, чем записей;
- готовый top быстрее, чем сортировка на каждый запрос.

Компромиссы:

- top может обновляться с небольшой задержкой;
- задержка ограничена фоновым refresh;
- для виджета задержка в пределах секунд приемлема.

### NATS Core вместо Kafka

Причина выбора:

- простой запуск через Docker Compose;
- низкая задержка;
- минимум инфраструктурной сложности;
- хорошо подходит для тестового задания.

Компромисс:

- NATS Core не даёт полноценный replay как Kafka;
- если consumer был выключен, опубликованные сообщения могут быть потеряны;
- для production с жёсткими гарантиями лучше Kafka или NATS JetStream.

### Stop-list в памяти

Причина выбора:

- проверка за O(1);
- stop-list обычно меньше потока событий;
- можно менять список без перезапуска.

Компромиссы:

- после рестарта stop-list очищается;
- между несколькими репликами список не синхронизируется;
- для production лучше Redis/PostgreSQL/config-service.

### Простая anti-abuse эвристика

Причина выбора:

- постановка не задаёт точный критерий аномалии;
- ML/сложный антифрод выходит за рамки тестового;
- ограничение одинаковых запросов от одного 'user_id' понятно и тестируемо.

Компромисс:

- не ловит распределённую накрутку большим количеством аккаунтов;
- возможны false positive;
- для production можно добавить ip_hash, session_id, device_id, user-agent и historical baseline.

### HTTP/JSON вместо gRPC

Причина выбора:

- проще проверить через curl/Postman;
- удобно для frontend-виджета;
- ниже сложность проекта;
- ответ читается человеком.

Компромисс:

- JSON тяжелее protobuf;
- gRPC был бы полезен для внутреннего backend-to-backend API;
- для этой задачи HTTP/JSON выбран как более простой клиентский интерфейс.

### Безопасность

В проекте сделано:

- NATS закрыт token auth в локальном окружении;
- stop-list API закрыт 'X-Admin-Token';
- есть timeout'ы HTTP server;
- ограничен 'limit' в '/top';
- ограничен размер payload из брокера;
- валидируются 'event_id', 'user_id', 'query';
- метрики не содержат user_id, session_id, ip_hash и сырые события.

Для production осталось:

- TLS/mTLS;
- broker ACL на publish/subscribe;
- внешний storage для stop-list;
- distributed anti-abuse;
- network policy для '/metrics'.

### Итог

Архитектура оптимизирована под быстрые чтения '/top', простой локальный запуск и понятную бизнес-логику.

Основные компромиссы сделаны в пользу:

- низкой задержки чтения;
- простого запуска;
- понятного кода;
- явного описания ограничений.
